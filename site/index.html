Manent: la memoria degli agenti AI come file che restano

Un vault Markdown (Obsidian-compatibile), versionato in git, diventa una memoria interrogabile, lintata e servita via MCP a qualunque agente: Claude, ChatGPT, Cursor, il vostro. Niente database proprietario, niente lock-in. Il retrieval è deciso a numeri, non a intuito.

Il problema

Il contesto evapora. La memoria di oggi o è opaca o è disordinata.

Due strade sul mercato, entrambe con un difetto strutturale.

Il database vettoriale che «estrae» la memoria

Ricordi trasformati in embedding e righe di un DB proprietario: non li leggi, non li diffi, non li correggi a mano, non li porti via. Nessuna pista di controllo su chi ha scritto cosa.

La pila di note senza schema

Leggibile, sì. Ma senza contratto: nessuna qualità di recupero garantita, nessun lint, nessun modo di sapere se una nota nuova rompe tutto.

La terza via: Manent

File Markdown come unica verità; indici, grafi ed embedding derivati e ricostruibili. Git come sincronizzazione e audit. Uno schema chiuso e versionato, lintato in CI. MCP come strato di accesso.

Come funziona

Dal file all'agente, in cinque pezzi

Ogni pezzo è un package del monorepo TypeScript. Tutto ricostruibile dai file.

Spec v0.2

Undici tipi di nota, frontmatter con schema JSON 2020-12, archi tipizzati (provenance, supersedes, contradicts), campo audience per la visibilità. Il codice segue la spec, mai il contrario.

Eval harness

Tre tipi di query (curate, oblique, automatiche), recall@k / MRR / nDCG, gate di regressione in CI: nessun cambio al ranking senza un numero prima e dopo.

Retrieval locale

BM25 ben tokenizzato più embedding multilingual-e5-small eseguiti in locale (nessuna API, nessun testo che esce), fusi per rango. Default che funziona senza dipendenze opzionali.

Due ere MCP

La revisione 2026-07-28 (stateless, input_required) e quelle con handshake, come due implementazioni separate con i tool definiti una volta sola. Si collega da claude.ai via OAuth 2.1.

Misurato, non intuito

Cosa dicono i numeri su un vault vero

479 note atomiche in italiano, 28 query scritte a mano (20 vicine al lessico della nota, 8 «oblique» che chiedono il concetto senza le sue parole) + 443 derivate dalle descrizioni. Misure del 4 settembre 2026.

Rankercurated hit@1curated MRRoblique MRRauto hit@1
BM25, tokenizer ingenuo35,0%0,5570,00096,8%
BM25 + stopword, prefix/fuzzy solo su termini lunghi70,0%0,8380,06397,3%
Denso (e5-small locale, un passaggio per nota)80,0%0,8920,15095,3%
Fuso: lessicale 1 : denso 2 (RRF)90,0%0,9420,17896,4%

Sul vault di agosto (305 note) la stessa configurazione fusa faceva 100% hit@1 sulle query curate. Crescere da 305 a 479 note è costato 10 punti: un numero da tenere sotto controllo, non da nascondere. È il motivo per cui esiste il gate di regressione.

  1. Il tokenizer valeva 35 punti. Stopword tolte e prefix/fuzzy attivi solo su termini lunghi: da 35% a 70% di hit@1 prima di qualsiasi cosa «intelligente». Con il prefix sempre attivo, di matcha diritto, disposizione, documento e le note lunghe vincono per rumore accumulato.
  2. Il grafo non paga. Personalized PageRank sui wikilink: zero guadagno sulle query curate, ~5 punti persi sulle automatiche. PPR amplifica un seed buono, non lo crea. Resta opt-in.
  3. Lessicale e denso sbagliano in direzioni opposte, quindi fonderli batte entrambi: 70% e 80% da soli, 90% fusi. Il bilanciamento va rimisurato quando il vault cresce: ad agosto il denso a peso doppio batteva i pesi pari di 20 punti, sul vault di settembre pareggiano. Con l'harness è un comando, non una decisione.
  4. Il chunking ingenuo peggiora. Spezzare ogni nota in passaggi con max-pooling regala a ogni nota lunga una chance per passaggio di matchare per caso: ad agosto costava 10–15 punti di hit@1, a settembre azzera la recall obliqua (MRR 0,181 → 0,038). Un'aggregazione corretta per lunghezza o pochi passaggi per nota lo recuperano; il prefisso contestuale (titolo + descrizione su ogni chunk) resta obbligatorio, senza crolla tutto.
Un vault, più agenti

Chi legge cosa, chi scrive dove, e cosa il brain non sa

Dal vault personale al cervello aziendale: customer care, agenti di coding, direzione. Stesso vault, non stessa vista.

Identità → vista, prima dell'indice

Ogni credenziale (token del vault, token di un agente, OAuth per entrambi) diventa un'identità. La sua vista è costruita dalle note che può leggere prima che esista un indice: search, grep, lettura grezza e vicinato non possono scavalcare il filtro, perché per quel lettore la nota non è mai stata caricata.

Privato per default

La visibilità sta nel frontmatter (audience: [tech, product]), non nella cartella: la stessa nota serve a due pubblici. Una nota che non dice nulla è privata. Un refuso rende una nota meno visibile, mai di più.

Scritture in quarantena, con conferma

Ogni scrittura è scansionata prima del disco: dati personali o testo che «parla al modello» vengono rifiutati (git è per sempre). Le note degli agenti finiscono in quarantena, private, finché una persona le promuove. Su MCP 2026-07-28 la scrittura chiede conferma con input_required: l'agente propone, la persona conferma.

Il registro dei buchi

Per imparare da chi chiede non serve il suo testo: serve sapere quali domande sono rimaste senza risposta. Ogni ricerca è registrata redatta e raggruppata per significato; una lettura che segue la marca «utile». Chiudere un buco con una nota produce una query del golden set che nessuno riuscirebbe a scrivere a mano.

Quickstart

Provalo in tre comandi

Node ≥ 20 (≥ 22.5 per il registro dei buchi). Nessuna chiave API.

git clone https://github.com/colopisalvatore/manent && cd manent
npm install && npm run build
node packages/cli/dist/index.js init my-vault      # scaffold di un vault
node packages/cli/dist/index.js lint my-vault      # lo schema come cancello
node packages/cli/dist/index.js serve my-vault     # MCP su stdio, hot reload

# da Claude Code
claude mcp add mybrain -- node <repo>/packages/cli/dist/index.js serve <vault>

# remoto, con identità per agente, registro e audit
node packages/cli/dist/index.js serve my-vault --http 3939 --token <token> \
  --retriever fused --agents agents.json --gaps gaps.sqlite --audit audit.jsonl

Hai già un vault Obsidian? Aggiungi name, description e type al frontmatter e lancialo: il lint ti dice il resto. Il README ha la spec, le misure complete e la roadmap.

Paper

Il preprint con metodo, ablazioni e limiti

Manent: File-First, Git-Versioned Memory for AI Agents. Specification, evaluation harness, and retrieval ablations on atomic notes.

Un paper di sistemi con valutazione empirica: la spec, l'harness a tre tipi di query, le ablazioni sul ranking (tokenizzazione, grafo, fusione, chunking), il registro dei buchi come modo di imparare dalle domande senza conservarle, e il modello di identità con il filtro prima dell'indice. I limiti sono detti chiaramente: un solo corpus, un golden set piccolo scritto dall'autore, nessuno studio con utenti.

Roadmap

Fatto e da fare

Nell'ordine in cui è stato costruito, e in cui andrà costruito.

  • Spec + lint + grafo + BM25 + server MCP stdio
  • Eval harness a tre query, gate di regressione
  • Embedding locali + fusione RRF
  • HTTP stateless, OAuth 2.1, collegamento da claude.ai
  • Due ere di protocollo come implementazioni separate
  • Registro dei buchi → golden set «oblique»
  • Spec v0.2: audience, author, quarantena
  • Identità per agente, viste filtrate prima dell'indice, audit
  • Scrittura dietro conferma (input_required)
  • Hot reload del vault
  • Promozione dalla quarantena (manent promote)
  • Curation: dedup per cluster, contraddizioni, comunità → MOC
  • Ricetta di deploy git-backed (post-receive → lint gate)
  • npm publish + CI
  • Tasks extension e MCP Apps
